# Database Migrations Guide

This directory contains version-controlled Supabase database schema migrations. All schema changes must be captured as SQL migration files to ensure reproducibility and enable safe version control.

## Quick Start

### Prerequisites

Install Supabase CLI:

```bash
brew install supabase/tap/supabase  # macOS
# OR
scoop install supabase              # Windows (with scoop)
# OR follow https://supabase.com/docs/guides/cli
```

### Local Development Setup

1. **Initialize Supabase locally:**

```bash
supabase start
```

This starts:
- PostgreSQL database on localhost:54322
- Supabase API on localhost:54321
- Studio on localhost:54323

2. **Link to your Supabase project:**

```bash
supabase link --project-ref foubokcqaxyqgjhtgzsx
```

When prompted, enter your database password from Supabase dashboard.

3. **Pull existing schema from production:**

```bash
supabase db pull
```

This creates a new migration file with the current production schema.

4. **Apply migrations locally:**

```bash
supabase db reset
```

This:
- Clears local database
- Runs all migrations from `migrations/` in order
- Seeds data (if `supabase/seed.sql` exists)

## Making Schema Changes

### Standard Workflow

1. **Make changes in Supabase Studio (locally or production)**

For local testing:
- Open http://localhost:54323
- Make changes directly in Studio
- Test changes locally

2. **Create a migration from your changes:**

```bash
# Pull the new schema and auto-create migration
supabase db pull
```

Or manually create a migration file:

```bash
supabase migration new add_user_roles_table
```

3. **Review the generated migration:**

```bash
cat supabase/migrations/20260505120000_add_user_roles_table.sql
```

Ensure:
- All changes are present
- No accidental data loss
- RLS policies are included

4. **Apply to local database:**

```bash
supabase db reset  # Start fresh and apply all migrations
```

Or push individual migration:

```bash
supabase migration up
```

5. **Test the application:**

```bash
flutter run
```

Ensure app still works with new schema.

6. **Commit migration:**

```bash
git add supabase/migrations/20260505120000_add_user_roles_table.sql
git commit -m "Add user roles table"
```

7. **Push to production (when ready):**

```bash
supabase db push --linked
```

Verify in Supabase dashboard that migration was applied.

## Migration File Naming

Migrations are named with timestamp prefix: `YYYYMMDDHHMMSS_description.sql`

Example:
- `20260503000000_fix_all_rls_recursion.sql`
- `20260504140000_review_remediation_rls_storage_posts_products.sql`

**Format is auto-generated by Supabase CLI.**

## Breaking Changes

If your migration includes breaking changes (deletions, renames, constraint additions), document them:

1. **In migration file:** Add a comment at the top:

```sql
-- BREAKING CHANGE: Deletes product_categories table
-- Migration strategy: Products will have categories stored in products.category_tags instead
-- Client impact: Update ProductModel to read from category_tags
-- Timeline: Must ship by 2026-06-01
```

2. **In git commit message:**

```
BREAKING: Delete product_categories table (#123)

- Products now store categories in category_tags (JSONB)
- Client code updated to read ProductModel.categoryTags
- Backward-compatible through migration grace period until 2026-06-01
```

3. **Notify team:**

Ping #engineering in Slack with migration details and client update timeline.

## Common Operations

### Inspect current schema

```bash
# List all tables
supabase db tables

# Get table schema
supabase db schema get -t pets

# List all migrations
supabase migration list
```

### Rollback (local only)

```bash
# Reset and re-apply all migrations
supabase db reset

# Or revert just the most recent
supabase db reset --version <timestamp>
```

### Squash migrations

Once in production, you can optionally squash old migrations:

```bash
supabase migration squash
```

This combines all migrations into a single file, making local setup faster.

## Production Safety

### Before pushing to production

1. **Test locally:**

```bash
supabase db reset  # Apply all migrations to fresh local DB
flutter run        # Test entire app workflow
```

2. **Review in dashboard:**

```bash
supabase link --project-ref foubokcqaxyqgjhtgzsx
```

Then inspect in https://app.supabase.com to verify schema.

3. **Backup production:**

In Supabase dashboard → Settings → Backups → Create backup

4. **Push migration:**

```bash
supabase db push --linked
```

### During production push

- Push during **off-peak hours**
- Have a team member on standby to monitor
- Be ready to rollback if critical issues occur

### Rollback on production

If migration causes issues, restore from backup in Supabase dashboard:

Settings → Backups → Restore

## Continuous Integration

The migration workflow is validated in CI:

```bash
# GitHub Actions (.github/workflows/db-migrations.yml)
supabase db reset      # Verify all migrations apply cleanly
supabase db lint       # Check for schema issues
```

If CI fails:
1. Fix the migration file
2. Commit and push
3. CI re-runs automatically

## FAQ

**Q: I made a change in production by mistake. How do I fix it?**

A: Restore the backup, then create a migration to fix it:

```bash
supabase db pull          # Get new schema
# Review the migration file
git add migrations/...
git commit -m "Fix accidental production change"
supabase db push --linked # Reapply
```

**Q: Should I commit migration files to git?**

A: **Yes, always.** Migrations are your source of truth for schema. Without them, you can't:
- Onboard new developers (they can't reproduce the schema)
- Track schema history (no git blame)
- Detect drift (PR diffs won't show DB changes)

**Q: Can I manually edit a migration file?**

A: **Yes, but be careful.** Only edit:
- SQL syntax errors
- RLS policy bugs
- Comment improvements

**Never edit:**
- Table/column names (create a new migration instead)
- Data in production (migrations are for schema only)

**Q: How do I handle concurrent schema changes?**

A: Each developer creates their own migration. When merging:
1. Pull latest migrations
2. Rebase your migration on top
3. Test locally: `supabase db reset`
4. Commit and push

Supabase will apply migrations in timestamp order.
